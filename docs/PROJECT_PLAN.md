# 專案規劃 v0.2

日期：2026-09-22
狀態：規劃定案，第一步實作開始。本文件所有數字都是設計起始值或待測目標，不是已達成的結果。

## 1. 目標

一個全自動的 AI 直播主，在 Kick 上播放預先錄好的遊戲影片，用固定角色的聲音講得像現場正在玩：說心得、講當下狀況、有反應。同時即時讀 Kick 留言，適時回覆並做出反應。直播從開播到收播沒有真人在場。

人工只做兩件事：事前把遊戲影片錄好，以及把影片、角色設定、金鑰與費用上限準備好。

觀眾看到的是連續的遊戲畫面，聽到的是對當下情境有反應的主持聲音。每次發言 1 至 3 句，有內容才說，容許停頓，不用罐頭台詞填空。

## 2. 兩條規則

1. **身分問題不回、也不撒謊。** 觀眾問「你是 AI 嗎」、「是不是機器人」這類問題，程式歸類為不回覆的留言，直接略過。反過來，程式不主動宣稱自己是真人；「我是真人」、「我不是 AI」這類句子在播出前會被驗證器擋下。角色用第一人稱講遊戲感受屬於表演，允許。
2. **不用真人的複製聲音。** 只用語音服務提供的合成聲音。

## 3. Kick 相關查證（2026-09-22）

來源：https://docs.kick.com/ 、https://docs.kick.com/events/event-types 、https://docs.kick.com/events/subscribe-to-events.md 、https://kick.com/community-guidelines

已確認：
- Kick 有官方開發者 API，事件以 webhook 方式送到開發者登記的 HTTPS 網址。留言事件名稱為 `chat.message.sent`，內容含 message_id、sender、content、created_at、replies_to。
- 訂閱事件用 `POST /public/v1/events/subscriptions`，需要帶 `events:subscribe` scope 的使用者 token 或 app token。未驗證的 app 對 chat.message.sent 有 1,000 個訂閱的上限，單一頻道遠低於此。
- 另有 livestreams 端點與 `livestream.status.updated` 事件，可用來確認直播狀態。
- 社群守則：「任何使用 AI 生成擬真內容的直播，應透過直播標題或畫面上的標示向觀眾清楚揭露」；「不得製作或分享會誤導觀眾的合成媒體，包括深偽或聲音複製」；「欺騙或不真實行為不被允許」。守則沒有針對預錄內容當直播播出的條文，也沒有針對聊天機器人的條文。

未確認：webhook 簽章驗證方式、重送政策、OAuth 申請流程細節、推流（RTMP）端點與串流金鑰取得方式。這些在第三階段接 Kick 時再查。

結論：留言讀取有官方路徑，不需要爬網頁。AI 標示是守則要求；是否標示由使用者決定，程式提供角落標示或標題文字的選項。

## 4. 系統架構

### 4.1 兩種部署方案

| | 方案 A：使用者電腦 | 方案 B：雲端主機（建議） |
| --- | --- | --- |
| 影片播放與推流 | OBS | 程式用 ffmpeg 直接把影片加主持聲音推到 Kick |
| 留言接收 | 需要對外通道讓 Kick webhook 進到家用電腦 | Kick 直接送到主機 |
| 無人值守可靠度 | 受電腦睡眠、更新、家用網路影響 | 主機 24 小時開著 |
| 聽得到聲音 | 直接聽 | 不能直接聽，用輸出測試影片檔的方式驗收 |
| 費用 | 無額外費用 | 每月數美元到二十美元等級 |

第一步（離線 mock）與兩種方案無關。第二步輸出測試影片檔在任何環境都能做。第三步起採方案 B，方案 A 保留為替代路徑，不再另外設計 OBS 音訊擷取。

### 4.2 模組分工

```
影片檔 ──► 事前預看（Planner）──► 講評計畫（每段要講什麼）
                                       │
影片時間軸 ──► 畫面來源（每 2 秒一張，縮到 960x540）──┐
Kick webhook ──► 留言來源 ──► 去重 ──► 本機分類 ──────┤
                                                       ▼
                                   Director：候選槽（最多一筆）、節流、TTL、狀態機
                                                       │
                                   模型：依角色、計畫、畫面、留言決定要不要說、說什麼
                                                       │
                                   驗證器：schema、ID、句數、長度、格式、禁語、重複、時效
                                                       │
                                   語音合成 ──► 播放器（一次只播一句）──► 混音進推流
```

五個可替換介面：FrameSource、ChatSource、ModelProvider、TtsProvider、AudioPlayer。每個都有 mock 版本。

### 4.3 事前預看與現場反應的分工

預錄影片是這個案子的優勢。開播前 Planner 用較低頻率走完整支影片，產生每一段的「可講的事」：發生了什麼、可能的感想、要避免講的（例如尚未發生的結果）。開播時 Director 把「目前影片時間對應的計畫」與「最近留言」一起給模型，模型決定當下說什麼。這樣講評更準、成本更低，也不會把後面才發生的事提前講出來。

### 4.4 Director 規則

- 畫面每 2 秒取樣、留言即時進入；模型最快每 5 秒呼叫一次，每分鐘最多 12 次。這些是待測值。
- 候選槽最多一筆，用最新有效事件替換。同時最多一個生成工作、一個播放工作；播放完才生成。採集在生成與播放期間持續進行。
- 優先序：可回答的新留言 > 計畫中的畫面事件 > 有新資訊的空檔。沒有候選就安靜。
- 留言 30 秒失效、畫面事件 12 秒失效，於送模型前、送語音前、播放前各檢查一次。
- contextVersion：影片段落切換（換局、換關）時遞增；舊版本的觀測與回覆一律丟棄，即使還在 TTL 內。
- sessionGeneration：暫停、急停、停止、來源重連、進入 ERROR 時遞增。所有非同步完成、錯誤與 finally 修改狀態前都要比對工作 ID 與 generation，晚到的結果不能改回狀態。
- 去重鍵為 source + messageId；seen、selected、spoken 三個集合分開；spoken 在實際播放開始時記錄。
- 狀態：STOPPED、IDLE、GENERATING、SYNTHESIZING、PLAYING、PAUSED、ERROR。非法轉換是程式錯誤，要記錄不能靜默。

### 4.5 本機分類與驗證

留言進入時先做本機粗篩：
- 空白、超長：不送模型，記 invalid_input。
- 身分提問：記 skipped_identity，不送模型，不計入可回答事件。
- 指令注入（要求忽略規則、讀出提示詞、開網址、執行指令）：記 unsafe_input_local，不送模型。
- 其餘視為可回答事件。

模型輸出只回 JSON：speak、utterance、reply_to_ids、observation_id、reason_code。驗證順序：
1. schema 與型別。
2. observation_id 對應本輪、reply_to_ids 全在本輪送入的清單內。
3. speak=false：utterance 必須為空、reply_to_ids 必須為空，直接回 IDLE，不呼叫語音，不算 provider 失敗。
4. speak=true：去除首尾空白後非空；以句號、問號、驚嘆號、換行切句後 1 至 3 句；長度以 Unicode code point 計、不含空白，最多 80；20 字是目標不是下限，「漂亮！」這種短句可播。
5. 禁用格式：Markdown 記號、條列、破折號、程式碼圍欄、「根據截圖」類措辭。
6. 禁語：宣稱真人的句型。
7. 與最近 10 句已播內容正規化後不得相同。

任一項不過就丟棄並記錄原因，不硬切、不改寫。

### 4.6 無人值守的守門機制

| 情況 | 行為 |
| --- | --- |
| 模型逾時 | 本事件不重試，短暫冷卻後處理新事件 |
| 模型 429 含 retry-after | 依 retry-after 冷卻，不重試舊事件 |
| 額度用盡 | 停止所有付費呼叫，影片繼續播，角色安靜 |
| 語音合成失敗 | 不播半成品，記錄失敗，不自動換供應商 |
| 播放裝置或推流異常 | 進入 ERROR，冷卻後自動嘗試復位一次；復位後丟棄舊回覆 |
| 連續三次 provider 失敗 | 暫停該來源 30 秒再探測 |
| 費用達上限 | 停止新付費呼叫，影片繼續播 |
| 影片播完 | 自動收播，或依設定接下一支 |
| 留言來源斷線 | 仍可依計畫講評，記錄來源離線 |

### 4.7 預算

費用 = 模型呼叫數 × 每次（文字 token + 圖片 token）× 單價 + output token × 單價 + 語音字元數 × 單價。圖片 token 依官方公式 ⌈寬/28⌉ × ⌈高/28⌉，960x540 約 700 token。

每次呼叫前先預留（含最大 output 與圖片），完成後結算；逾時以預留額結算，不假定零費用。每小時與每場上限為 null 時代表未授權，付費模式不能啟動。第一步只用假費率驗證預留與結算邏輯。上游估算的每小時約 2 至 4 美元是情境估算，不是上限。

## 5. 階段與驗收

### 第一步：離線 mock（現在）

在沒有任何設備與金鑰的環境完成：
- TypeScript + Node.js 22 專案，五個介面的 mock 實作，Director、驗證器、去重、預算、JSONL 日誌、CLI。
- 可重生的合成 fixture：至少 100 則唯一穩定 ID 的留言，含重送、跨來源同 ID、不同人同句、隔 60 秒同句、身分提問、指令注入、無關、空白與超長、留言中斷；畫面含換局、黑畫面、停更；provider 故障排程。
- 一個命令重播 30 分鐘「場景時間」，用虛擬時鐘加速；報告同時列場景時間與實際 wall time。
- 報告輸出：唯一可回答事件數、播出回覆數、留言覆蓋率（不超過 100%）、遊戲評論另計、丟棄分類、四段延遲的中位數與 p95 及樣本數、重播次數（必須 0）、重疊次數（必須 0）、急停統計、預算統計。
- 必測：合法安靜不觸發語音；短句可播；跨來源同 ID 不衝突；同來源重送不重播；最多一個模型與一個播放；候選槽有界；換局後舊評論不播；pause/stop 後晚到結果不復活；resume 不受舊工作污染；10 次急停無晚到播放；預算預留不超上限；覆蓋率不超過 100%；宣稱真人的句子被擋。

驗收：npm ci、build、test 退出碼 0；replay 與 report 可重跑且結果一致；報告寫入 reports/。

### 第二步：真實內容，輸出測試影片

接真影片（ffmpeg 抽幀）、真模型（Claude，圖片輸入，結構化輸出，SDK 重試關閉）、真語音（Azure zh-TW 或 ElevenLabs，選一個），Planner 預看整支影片。留言仍用 fixture。輸出「影片 + 主持聲音」的 mp4 供使用者檢視。使用者需提供影片檔、金鑰放置方式、角色設定與費用上限。

驗收：使用者看過測試影片，對自然度、相關性、角色一致性各給 1 至 5 分；量測每次呼叫的實際 token 與費用。

### 第三步：接 Kick，雲端試播

Kick 開發者應用程式、OAuth 授權、webhook 接收、事件訂閱、推流到 Kick。在雲端主機做短時間試播，有人在旁監看。使用者需完成 Kick 應用程式註冊與授權、提供串流金鑰、決定 AI 標示方式。

驗收：留言從送出到聲音回覆的實際秒數；推流穩定；守門機制在人為製造的故障下正常運作。

### 第四步：全自動

連續兩小時無人值守測試：來源中斷與恢復、費用守限、影片結束自動收播。通過後才真正放手。

## 6. 風險與未知

- AI 對該款遊戲畫面的理解程度未測。
- 聲音自然度未試聽。
- 留言到回覆的實際延遲未量測，設計目標中位數 6 秒、p95 12 秒。
- Kick 守則要求 AI 擬真內容標示。不標示的風險由使用者承擔；程式提供標示選項。
- Kick webhook 需要公開網址；家用電腦方案要多一條對外通道。
- 費用隨呼叫次數線性增加，必須設上限。

## 7. 需要使用者親自做的事

1. Kick 開發者後台註冊應用程式，用直播帳號授權。
2. 取得 Kick 串流金鑰。
3. 申請 Claude API 金鑰並設定付費上限。
4. 選一家語音服務並申請金鑰。
5. 準備遊戲影片檔。
6. 決定角色：名字、個性、說話風格、聲音、禁忌。
7. 決定每場與每小時的費用上限。
8. 決定是否放 AI 標示以及放的方式。

金鑰只放在執行環境的設定檔或環境變數，不進 GitHub。本 repo 公開，只放合成 fixture，不放真實留言、錄影或帳號資料。
